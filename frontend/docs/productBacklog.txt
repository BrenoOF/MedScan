# **MedScan — Requisitos Específicos do Product Backlog Frontend**

**Objetivo:** transformar os 15 itens do Product Backlog em requisitos técnicos menores, específicos e verificáveis, relacionados a partes concretas da aplicação React.

Nesta etapa, o foco continua sendo **corrigir e estabilizar o frontend existente**, sem implementar antecipadamente funcionalidades que dependem de novos endpoints do backend.

Cada requisito terá um identificador próprio, permitindo organizar o desenvolvimento em tarefas no Trello, Jira, GitHub Projects ou em uma planilha.

## **1. Estrutura do projeto e comunicação com o backend**

Backlogs FE-01, FE-02 e FE-03 | Prioridade P0

### **FE-01 — Definir e organizar a estrutura oficial do frontend**

**Parte da aplicação:** estrutura geral, diretórios, componentes e configuração do React.

| ID      | Requisito específico                                                                              | Critério de aceitação                                                                  |
| ------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| FE-01.1 | Comparar as duas versões do frontend e escolher aquela que será utilizada como projeto principal. | Existe uma única versão oficial para desenvolvimento.                                  |
| FE-01.2 | Identificar as páginas, componentes e serviços que podem ser reaproveitados da outra versão.      | Componentes aproveitáveis estão identificados, sem duplicação de implementações.       |
| FE-01.3 | Revisar a organização das pastas `pages`, `components`, `services` e `assets`.                    | Cada arquivo possui uma responsabilidade clara e está localizado de forma consistente. |
| FE-01.4 | Verificar dependências e configurações existentes no `package.json`.                              | O projeto instala suas dependências, inicia e executa o build sem erros.               |

### **FE-02 — Configurar a conexão com a API Spring Boot**

| ID      | Requisito específico                                                                           | Critério de aceitação                                                          |
| ------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| FE-02.1 | Definir um endereço base único para as chamadas à API, considerando o context path `/MedScan`. | Nenhum componente precisa repetir manualmente a URL completa do backend.       |

| FE-02.4 | Verificar a compatibilidade entre origem do frontend, CORS e cookies.                          | O navegador consegue realizar as requisições permitidas sem bloqueios de CORS. |

**Arquivos envolvidos:** `vite.config.js`, `.env` quando aplicável, `src/services/` e configuração correspondente do Spring Boot.

### **FE-03 — Padronizar as requisições HTTP**

**Parte da aplicação:** camada de comunicação com o backend.

| ID      | Requisito específico                                                                             | Critério de aceitação                                                              |
| ------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| FE-03.1 | Centralizar o tratamento das requisições realizadas com `fetch` ou biblioteca HTTP já utilizada. | As requisições seguem um padrão único.                                             |

## **6. Ordem de execução por área da aplicação**

Para evitar corrigir partes isoladas que dependem umas das outras, recomendo seguir esta sequência:

1. **Estrutura e inicialização**

   FE-01, FE-06, FE-11

   Definir projeto oficial, corrigir navegação e eliminar referências inexistentes.
2. **Comunicação com Spring Boot**

   FE-02, FE-03

   Estabelecer uma única configuração HTTP, com sessão e tratamento correto de respostas.
3. **Login, cadastro e sessão**

   FE-04, FE-05, FE-07, FE-08

   Garantir autenticação real e controle de acesso coerente com o backend.
4. **Dados e formulários**

   FE-09, FE-10, FE-13

   Corrigir DTOs, integrar dados disponíveis e impedir submissões inconsistentes.
5. **Interface e qualidade**

   FE-12, FE-14, FE-15

   Padronizar feedback, responsividade e executar testes.

## **8. Critério final para considerar o frontend estruturado**

O frontend estará pronto para a próxima etapa quando:

- Houver uma única versão oficial, com dependências e navegação funcionando.
- Login, cadastro, logout e recuperação de sessão utilizarem a API real.
- As operações existentes não apresentarem sucesso simulado.
- Os formulários integrados utilizarem os DTOs corretos.
- Os perfis tiverem navegação coerente com suas permissões.
- As requisições e seus erros forem tratados adequadamente.
- As telas existentes funcionarem em celular e computador.
- Os testes básicos de frontend e integração tiverem sido executados com resultados satisfatórios.

**Resultado esperado:** uma base React organizada e funcional para as operações já suportadas pelo backend, pronta para receber as próximas funcionalidades do MedScan sem depender de uma reconstrução.

Depois dessa estabilização, será possível criar backlogs próprios para os módulos **Paciente, Agendamento, Atendente, Administrador e Busca Ativa**, com requisitos funcionais detalhados e critérios de aceitação, sem misturá-los às correções da estrutura atual.
